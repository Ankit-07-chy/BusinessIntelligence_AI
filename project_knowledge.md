# KPI Intelligence-to-Action Engine — Complete Project Knowledge

## 1. Project Overview

This project is a **KPI Intelligence-to-Action Engine** for an e-commerce business.

The system detects material KPI movements, explains likely root causes, generates persona-specific narratives, recommends practical actions, captures feedback, and logs telemetry.

The system is built as a hosted full-stack application:

- Frontend: **Next.js + TypeScript**
- Backend: **FastAPI + Python**
- Database: **PostgreSQL**
- Analytics: Deterministic SQL, statistical models, contribution analysis, and confidence scoring
- LLM: Used only for orchestration, narrative generation, and intent understanding
- Hosting: Vercel / Render / Railway / Neon / Supabase / Docker

Core principle:

> The LLM is not the source of quantitative truth.  
> Numbers are generated by deterministic SQL, business rules, governed KPI contracts, statistical models, and analytics services.

---

## 2. Business Problem

Businesses track KPIs across fragmented systems:

- Sales / ERP
- Inventory / warehouse
- Marketing platforms
- Web analytics
- Finance systems
- Logistics systems

These systems have:

- Different refresh cadences
- Different grains
- Different data quality
- Different KPI definitions
- Different business calendars
- Different access restrictions

The problem is not just detecting that a KPI changed.

The real problem is:

1. Detecting material KPI movements.
2. Reconciling data across sources.
3. Identifying likely explanatory drivers.
4. Explaining the movement to the right persona.
5. Communicating uncertainty.
6. Recommending practical actions.
7. Learning from feedback.
8. Operating securely and cost-effectively.

---

## 3. Product Goal

Build a working prototype that answers:

```text
What changed?
Why did it change?
How confident are we?
Who should see it?
What should be done?
What evidence supports this?
How did the system behave operationally?
```

The engine should move from:

```text
Revenue is down 8 percent.
```

To:

```text
Revenue is down $420K versus forecast.
The largest supported driver is stockout in top SKUs.
A reduction in paid search spend is the second driver.
Confidence is high for stockout and medium for marketing.
Recommended action: expedite replenishment and review paid search budget.
Owner: Supply Chain Manager and Marketing Manager.
Monitoring: track stockout rate and paid clicks daily.
```

## 5. Chosen Domain

We choose **e-commerce / omnichannel retail** because it naturally connects:

- Revenue
- Marketing spend
- Web traffic
- Inventory
- Fulfillment
- Margin
- Promotions
- Seasonality

This makes it easy to simulate realistic multi-factor KPI movements.

## 6. Core KPIs

We will use 3 to 5 connected KPIs.

### 6.1 Net Revenue

Definition:

```text
Total sales after discounts and returns.
```

Formula:

```text
net_revenue = gross_revenue - discount_amount - returns_amount
```

Primary drivers:

- Stockouts
- Marketing spend
- Price changes
- Discounts
- Seasonality
- Competitor promotions

### 6.2 Gross Margin

Definition:

```text
Revenue minus cost of goods sold.
```

Primary drivers:

- Discounting
- Mix shift
- Cost changes
- Returns

### 6.3 Online Conversion Rate

Definition:

```text
Orders divided by sessions.
```

Formula:

```text
conversion_rate = orders / sessions
```

Primary drivers:

- Traffic quality
- Website issues
- Payment failures
- Product availability
- Promotion relevance

### 6.4 OTIF

Definition:

```text
On-Time In-Full fulfillment rate.
```

Primary drivers:

- Carrier delays
- Warehouse issues
- Inventory availability
- Demand spikes

### 6.5 CAC

Definition:

```text
Customer acquisition cost.
```

Formula:

```text
cac = marketing_spend / new_customers
```

Primary drivers:

- Channel spend
- Campaign efficiency
- Attribution lag
- New customer volume

## 7. Synthetic Data Strategy

We do not have access to a real dataset, so we will generate synthetic e-commerce data.

This is an advantage because we can inject known root causes.

Example injected incidents:

```text
Day 15:
- Stockout begins for top SKU.
- Paid search budget reduced by 20 percent.
- Competitor promotion starts.

Result:
- Revenue drops.
- Engine should detect stockout and marketing reduction.
```

This satisfies:

> One multi-factor KPI movement with known or simulated underlying drivers.

## 8. Data Sources

We simulate multiple sources.

| Source | Table | Grain | Refresh Cadence |
|---|---|---|---|
| Sales / ERP | fact_sales | product-store-day | Daily |
| Inventory / WMS | fact_inventory | product-store-day | Daily |
| Marketing Platform | fact_marketing_spend | campaign-day | Weekly with lag |
| Web Analytics | fact_web_traffic | channel-device-day | Hourly |
| Logistics | fact_shipments | order-line-day | Daily |
| Finance / Governance | kpi_definitions | KPI-level | Governed |
| Metadata | source_status | source-level | System-tracked |

## 9. Personas

The system must produce different narratives for different users.

### 9.1 CFO

Focus:

- Revenue impact
- Margin impact
- Financial risk
- Accountability
- Materiality

Preferred output:

- Executive summary
- Dollar impact
- Confidence
- Recommended approval action

Example:

```text
Revenue is $420K below forecast.
Primary driver is stockout in top SKUs.
Secondary driver is reduced paid search spend.
Recommended action: approve expedited replenishment.
```

### 9.2 Supply Chain Manager

Focus:

- Stockouts
- Inventory
- Replenishment
- Store/SKU detail
- Fulfillment

Preferred output:

- SKU-level details
- Store-level impact
- Purchase order actions
- Stock reallocation
- Monitoring plan

Example:

```text
Stockout rate increased from 3 percent to 14 percent.
Top affected SKUs are concentrated in EU stores.
Recommended action: expedite purchase order and reallocate inventory.
```

### 9.3 Marketing Manager

Focus:

- Campaign performance
- Traffic
- Spend efficiency
- Conversion
- CAC

Preferred output:

- Campaign-level impact
- Budget restoration
- Test-and-learn recommendation

Example:

```text
Paid search spend decreased 22 percent.
Conversion remained stable.
Likely impact is traffic loss.
Recommended action: restore budget and run incrementality test.
```

### 9.4 Analyst

Focus:

- Evidence
- Methodology
- Lineage
- Confidence
- Alternative hypotheses

Preferred output:

- Analytical method
- Data quality
- Assumptions
- Validation steps

| Layer | Technology |
|---|---|
| Primary Database | PostgreSQL |
| Local Analytics Optional | DuckDB |
| Migrations | Alembic |
| Seed Data | Python scripts |

### Analytics

| Layer | Technology |
|---|---|
| Data Processing | Pandas or Polars |
| Forecasting | Statsmodels or Prophet |
| Anomaly Detection | Custom residual / z-score logic |
| Contribution Analysis | Deterministic Python/SQL |
| Causal Inference | Simple control-group comparison |
| Confidence Scoring | Custom rules |

| Layer | Technology |
|---|---|
| LLM Provider | OpenAI-compatible API, Anthropic, Gemini, or Ollama |
| Structured Output | Instructor |

| Prompt Templates | Markdown or YAML |
| Guardrails | Evidence-only generation |

### Hosting

| Layer | Recommended Service |
|---|---|
| Frontend | Vercel |
| Backend | Render / Railway / Fly.io |
| Database | Neon / Supabase / Railway PostgreSQL |
| Local Dev | Docker Compose |
| CI/CD | GitHub Actions |

## 12. High-Level Architecture

```text
User
  |
  v
Next.js Frontend
  |
  | HTTPS / JSON
  v
FastAPI Backend
  |
  |----------------------------------|
  |                                  |
  v                                  v
Deterministic Analytics Engine     LLM Orchestration Layer
  |                                  |
  v                                  v
PostgreSQL                         Evidence Pack + Guardrails
```

### Request Flow

1. User opens dashboard or asks a question.
2. Frontend calls FastAPI.
3. Backend authenticates the user.
4. Security filters are applied.
5. KPI data is fetched from PostgreSQL.
6. Analytics engine calculates:
   - Actual vs forecast
   - Anomaly score
   - Materiality score
   - Driver contributions
   - Confidence score
7. Evidence pack is generated.
8. LLM generates narrative from evidence only.
9. Response is returned to frontend.
10. Telemetry is logged.
11. Feedback can be submitted and stored.

## 15. Analytics Engine

This is the non-LLM truth layer.

### 15.1 Baseline Forecast

For the prototype, use a simple baseline:

```text
expected_value =
  average of same weekday in previous 4 weeks
  + trend adjustment
  + seasonality adjustment
```

Optional:

```text
Statsmodels ETS
Prophet
```

### 15.2 Anomaly Detection

```text
residual = actual_value - expected_value
z_score = residual / historical_standard_deviation
```

Flag anomaly if:

```text
abs(residual) > absolute_threshold
AND abs(z_score) > statistical_threshold
AND data_quality_score > minimum_quality
```

### 15.3 Materiality Score

```text
materiality_score =
  statistical_score
  * business_impact_score
  * data_quality_score
```

Where:

```text
business_impact_score =
  normalized_abs_dollar_impact
  + margin_impact
  + strategic_weight
```

### 15.4 Data Quality Score

```text
data_quality_score =
  0.4 * completeness_score
  + 0.3 * freshness_score
  + 0.2 * consistency_score
  + 0.1 * validity_score
```

### 15.5 Driver Contribution

Example revenue bridge:

```text
total_revenue_change =
  volume_effect
  + price_effect
  + mix_effect
  + discount_effect
  + stockout_effect
  + marketing_effect
  + seasonality_effect
  + residual
```

For prototype, we can simplify:

```text
driver_contribution =
  estimated_impact_of_driver / total_kpi_change
```

### 15.6 Confidence Score

```text
confidence_score =
  0.30 * evidence_strength
  + 0.25 * data_quality_score
  + 0.20 * model_fit_score
  + 0.15 * causal_or_business_confirmation
  + 0.10 * freshness_score
```

Confidence labels:

```text
High: confidence_score >= 0.75
Medium: 0.50 to 0.75
Low: below 0.50
```

### 15.7 Driver Ranking

```text
driver_score =
  0.35 * estimated_impact_score
  + 0.25 * confidence_score
  + 0.15 * evidence_strength_score
  + 0.10 * actionability_score
  + 0.10 * business_relevance_score
  + 0.05 * timeliness_score
```

Penalties:

```text
driver_score -= contradiction_penalty
driver_score -= low_data_quality_penalty
driver_score -= stale_evidence_penalty
```

## 16. Abstention Logic

The engine must abstain when evidence is weak.

Abstain if:

```text
confidence_score < 0.5
OR key_source_missing = true
OR data_quality_score < 0.5
OR contradiction_score > threshold
OR security_filter_removed_critical_data = true
```

Example abstention response:

```json
{
  "status": "abstain",
  "confidence": "low",
  "summary": "Insufficient evidence to explain the KPI movement.",
  "missing_evidence": [
    "marketing_spend",
    "store_footfall"
  ],
  "clarification_question": "Were there store closures, tracking issues, or local events during this period?"
}
```

## 19. LLM Guardrails

System rules:

```text
1. Use only the evidence pack.
2. Do not calculate new numeric values.
3. Do not invent drivers.
4. If evidence is insufficient, abstain.
5. State confidence clearly.
6. Mention missing or delayed sources.
7. Adapt tone to the persona.
8. Do not reveal restricted fields.
9. Do not execute database queries.
10. Return only the required structured schema.
```

Recommended structured output:

```json
{
  "status": "success",
  "confidence": "high",
  "summary": "string",
  "primary_drivers": [],
  "evidence_citations": [],
  "uncertainties": [],
  "recommended_actions": [],
  "clarification_question": null
}
```

## 24. Evaluation Framework

### Golden Incident 1: Multi-Factor Movement

Scenario:

```text
Revenue drops because of stockout and marketing reduction.
```

Expected:

```text
Detect anomaly.
Rank stockout and marketing as top drivers.
Recommend replenishment and budget review.
```

### Golden Incident 2: Low Confidence

Scenario:

```text
Key sources are missing or delayed.
```

Expected:

```text
Low confidence.
Ask clarification.
Abstain from strong action.
```

### Golden Incident 3: Sparse History

Scenario:

```text
New product has only 2 or 3 weeks of history.
```

Expected:

```text
Use analogous products or category priors.
Show wide uncertainty.
Avoid overconfident explanation.
```

### Golden Incident 4: Security Scope

Scenario:

```text
Regional user requests global insight.
```

Expected:

```text
Restrict insight to permitted region.
Show scope limitation.
Log access.
```

```text
Detects material KPI movements.

Explains likely drivers with confidence.
Generates persona-specific narratives.
```
